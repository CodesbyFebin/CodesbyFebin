UI Design Systems: Polished Interfaces Without Generic AI Slop

Build premium interfaces using design systems, design tokens, typography, and the anti-slop rules that keep output intentional.

Why Design Systems Matter

A polished interface is the single biggest quality lever in any application. This skill governs the DOM UI: pages, chrome, HUD, menus, forms, modals. (For a 3D game's canvas, see the building-games skill; for 2D canvas, use native Canvas 2D.)

The difference between "looks generic" and "looks intentional" is not more assets or animations—it's defining a system once and composing from it. Never sprinkle ad-hoc values.

The fundamental rule: Define the system first (colors, type, spacing, radius), then compose everything from that system. One source of truth beats a thousand hex values.

Design-System-First: Tokens in CSS

Put your palette, radii, and fonts in one place—a CSS @theme block—and consume them as Tailwind utilities. Tailwind v4 is CSS-first, making this natural.

/* src/styles.css */
@import "tailwindcss";

@theme {
  /* Colors: primary + neutrals + optional accent */
  --color-bg: #0b0b0f;
  --color-surface: #16161d;
  --color-fg: #e7e7ea;
  --color-muted: #a0a0ab;
  --color-primary: #14b8a6;
  --color-border: #26262f;

  /* Spacing scale: 4/8-based */
  --spacing-xs: 0.25rem;
  --spacing-sm: 0.5rem;
  --spacing-md: 1rem;
  --spacing-lg: 1.5rem;
  --spacing-xl: 2rem;

  /* Radii */
  --radius: 0.75rem;

  /* Typography */
  --font-sans: "Inter", system-ui, sans-serif;
  --font-serif: "Georgia", serif;
}

Essential Tailwind v4 Fix: Buttons

Tailwind v4's Preflight makes <button> use cursor: default, which feels broken. Add this fix once in your styles:

@layer base {
  button:not(:disabled),
  [role="button"]:not(:disabled) {
    cursor: pointer;
  }
}

No Ad-Hoc Styling

  • ❌ No raw hex in JSX
  • ❌ No literal text-white or bg-black
  • ❌ No arbitrary values like p-[16px] or text-[13px]
  • ✅ Every value is a token or a scale step
// ❌ Wrong
<button className="bg-white text-black px-[16px] py-[8px]">
  Click me
</button>

// ✅ Right
<button className="bg-surface text-fg px-md py-sm">
  Click me
</button>

The Quantified Rubric: Cheap Rules That Prevent "Ugly"

These constraints sound limiting—they're actually liberating. They force intentional choices.

Rule Target Why
Color count ≤ 3–5 total One primary + neutrals + maybe one accent. No random hues.
Font families ≤ 2 (often 1) Pair display/heading with body, or use one. Consistency beats variety.
Line-height 1.4–1.6 for body Tighter for large headings. Readable text breathes.
Contrast Foreground set wherever background changes If you override background color, override text color too. Contrast must hold.
Mobile-first design ~390px layout first, then scale up No horizontal overflow. Forces ruthless prioritization.
Tap targets ≥ 44px Finger-friendly. Essential on mobile.
Spacing scale 4/8-based (xs/sm/md/lg/xl) Generous whitespace beats cramming. Rhythm feels natural.
Accent usage One accent, sparingly Used only for primary actions. Everywhere else is noise.

Anti-AI-Slop: The Red Flags

These are the tells that make output look generic or AI-generated. Avoid them religiously.

  • ❌ Gradient-blob filler. Giant hero gradients as a substitute for content. Looks lazy.
  • ❌ Emoji as icons. Use a real icon set (lucide-react). Emoji in a professional interface reads as "I didn't care to make real icons."
  • ❌ Hand-drawn SVG "illustrations." Maps, charts, doodles—use real libraries (recharts) or real generated images.
  • ❌ Placeholder images or lorem-gray boxes. Generate real images or use real content. Placeholder images scream "unfinished."
  • ❌ Overused fonts. Default system-only, or Comic Sans-tier picks. Pick one intentional typeface.
  • ❌ Decorative noise. Every element must earn its place. Cut clutter. Establish a system, then vary with intent—not randomness.
  • ❌ Inconsistent UI language. When editing an app in place, match the existing UI. Don't introduce a second visual language halfway through.
The slop detector: If you can't explain in one sentence why an element is there, delete it. Premium feels like every choice was intentional.

Typography: Type Scale and Rhythm

Typography is the backbone of hierarchy and readability. Get it right and the interface feels refined; get it wrong and everything feels amateurish.

Type Scale (Example)

/* Establish a consistent type scale */
h1: 48px, line-height 1.2, font-weight 700
h2: 36px, line-height 1.2, font-weight 600
h3: 24px, line-height 1.3, font-weight 600
body: 16px, line-height 1.6, font-weight 400
small: 14px, line-height 1.5, font-weight 400

Pairing Typefaces

  • Serif + sans-serif: Georgia (serif) for headings, System (sans) for body. High contrast, classic.
  • Sans + sans: Inter (body) + Poppins (display). Both modern, different weight gives variation.
  • Single typeface: Use one excellent font (Inter, Roboto, IBM Plex) and vary weight/size for hierarchy.

Running Text Width

Keep body text around 65 characters wide for readability. Longer lines fatigue the eye. Use a max-width container:

/* Keep text readable */
.content {
  max-width: 65ch;  /* ~65 characters */
  margin: 0 auto;
}

Layout & Hierarchy

Visual hierarchy tells users what matters. Size, weight, color, and space express importance.

  • One primary action per view. Everything else is secondary or tertiary. Use color and scale to express hierarchy.
  • Real layout structure. Use grid/flex and container max-widths. No absolute-position hacks.
  • Alignment to grid. Consistent grid (8px or 4px-based) keeps layouts cohesive.
  • Empty, loading, and error states. These are part of the design. Don't ship blank or janky intermediate states.
/* Proper layout structure */
<div className="max-w-4xl mx-auto px-lg py-xl">
  <h1 className="text-4xl font-bold mb-md">Main heading</h1>
  <p className="text-lg text-muted mb-lg">Supporting text</p>

  <button className="bg-primary text-bg font-semibold px-lg py-sm rounded">
    Primary action
  </button>
</div>

Motion: Subtle and Purposeful

Animation isn't decoration—it's communication. Use motion to guide attention, provide feedback, or ease transitions.

  • Duration: 150–250ms for hover/press/enter transitions. Longer feels sluggish; shorter feels twitchy.
  • Easing: Ease-in-out for UI transitions. Ease-out for entrances (things appear). Ease-in for exits (things disappear).
  • Respect prefers-reduced-motion. Some users request no animations for accessibility. Check the preference and disable motion if requested.
  • Avoid layout jank. Never animate layout properties (width, height, padding). Use transform/opacity instead (GPU-accelerated).
/* Smooth, accessible button transition */
button {
  transition: background-color 200ms ease-in-out;
}
button:hover {
  background-color: var(--color-primary-hover);
}

/* Respect reduced motion */
@media (prefers-reduced-motion: reduce) {
  button {
    transition: none;
  }
}

Game Overlays (When Paired With building-games)

If you're building a game with a 3D canvas, this skill styles the DOM overlay (start screen, HUD, pause menu). The canvas itself is owned by building-games.

  • Readable over the canvas. Use backdrop, contrast, and layers to keep UI legible.
  • Out of the pointer-lock path. Don't interfere with gameplay input.
  • Real icons, images, charts. No emoji, no placeholder boxes.

Finish Checklist

  • ☐ Tokens defined in @theme; no ad-hoc hex or arbitrary values in JSX
  • ☐ Color count ≤ 5 (one primary + neutrals + optional accent)
  • ☐ Font count ≤ 2; clear pairing or single typeface
  • ☐ Line-height 1.4–1.6 for body
  • ☐ Contrast holds everywhere; foreground overridden wherever background is
  • ☐ Mobile (~390px) has no horizontal overflow; tap targets ≥ 44px
  • ☐ Real icons, images, charts—none of the anti-slop tells
  • ☐ Empty, loading, error states handled
  • ☐ Motion 150–250ms, respects prefers-reduced-motion
  • ☐ Rendered and eyeballed in a browser (not just curl)
  • ☐ No generic/templated feel; every choice is intentional
