Building Secure Authentication Systems: OAuth and Identity

Engineering guide to OAuth 2.0, federated identity, email/password auth, session management, and security models for production systems.

Why This Matters

Authentication is the first security boundary between your system and its users. A well-designed auth system separates concerns cleanly: identity providers handle credentials, your app manages sessions and per-user data, and clear trust boundaries prevent both data leaks and impersonation attacks.

Poor auth design cascades: shared secrets in logs, session tokens leaked in URLs, cross-site request forgery (CSRF), session fixation, and permission confusion between users. This guide covers tested patterns that prevent these classes of bugs.

Core principle: Authentication (who you are) and authorization (what you can do) are separate concerns. Never conflate them. Identity is stable; permissions can change per request.

Architecture: Three Layers

Production auth stacks three distinct layers:

1. Identity Provider (IdP)

Handles credential storage and verification. In modern systems, this is never your own code—use a trusted third party:

  • OAuth 2.0 providers (Google, X/Twitter): Federated. Users sign in with an existing account; your app never sees credentials.
  • Email/password (Better Auth, Auth0): A managed service still handles the crypto and recovery flows. Building your own password hashing is a footgun.
  • Hybrid (recommended for most products): Offer both OAuth (frictionless onboarding) and email/password (account independence).

2. Session Broker

Mediates between identity provider and your app. Handles the OAuth handshake (SDP exchange), maintains a session after sign-in, and serves the current user on each request.

  • Uses cookies marked __Host- (HTTPS-only, same-site) or bearer tokens in the Authorization header.
  • Never leaks tokens in URLs or logs.
  • Validates the session on every protected request.

3. Your App's Authorization

Once a user is authenticated (session valid), your app enforces what that user can do:

  • Scope every database query to user_id: never trust a user-supplied ID without server-side verification.
  • Define roles and permissions explicitly in a table, not ad-hoc in code.
  • Assume the session is valid; the broker already verified it.
// PATTERN: Server function with auth middleware
export const listTodos = createServerFn()
  .middleware([authMiddleware])  // Verify session
  .handler(async ({ context }) => {
    // context.userId is verified by middleware
    const todos = await db`
      SELECT id, title FROM todos
      WHERE user_id = ${context.userId}
    `;
    return todos;
  });

OAuth 2.0: Federated Identity

Use OAuth 2.0 when you want users to sign in with an existing account (Google, X, etc.). Your app never sees their password.

The Flow

  1. User clicks "Sign in with Google"
  2. Browser opens a popup to Google's login screen
  3. User approves your app and Google redirects back with a temporary code
  4. Your server exchanges the code for a token (backend-to-backend, secure)
  5. Your app creates a session and the user is signed in
Security invariant: The exchange of code for token must happen server-to-server. Never expose tokens in the browser or URL. A popup is fine for the user-facing flow; the backend exchange is invisible.

Setup (High Level)

  • Register your app with Google/X developer consoles. Get a client ID and secret.
  • On your server, handle POST /api/auth/callback and exchange the code for a token.
  • Fetch the user's profile from the IdP.
  • Create or update a user record in your database.
  • Issue a session cookie/token to the client.
Step Player Security Notes
User initiates sign-in Frontend (popup) Redirect to IdP login; pop-up or full-page, both safe
IdP redirects with code IdP → Frontend Code is single-use, short-lived (minutes)
Exchange code for token Backend (server-to-server) Use client secret here; never expose in frontend
Create session Backend Issue secure, httpOnly cookie; never send token to client if avoidable

Supported Providers

Google and X (Twitter) are the recommended starting point. Both have straightforward OAuth implementations and high adoption. Never build OAuth yourself—use a library like better-auth or delegate to a managed service.

Email/Password: Account Independence

Use email/password for users who want account independence or as a fallback when OAuth is unavailable. Delegate password hashing to a managed service; never build it yourself.

The Pattern

  1. User submits email + password to your sign-up form.
  2. Your server validates email format and password strength, then sends it to a managed auth service.
  3. The service hashes the password (bcrypt, Argon2, etc.), stores it securely, and returns a user ID.
  4. On sign-in, verify the password against the service, not by fetching and comparing hashes yourself.
  5. Create a session and sign the user in.
Never hash passwords in your app code. Use a managed service (Better Auth, Auth0, Firebase) or a well-tested library with annual security audits. Hashing is a commodity; your app should not own it. 
// WRONG: Do NOT do this
const hash = crypto.createHash('sha256').update(password).digest('hex');
db.users.insert({ email, hash });

// RIGHT: Use a managed service
const user = await betterAuth.signUpEmail({
  email: data.email,
  password: data.password
});
// Service handles hashing, salting, verification

Session Management

After authentication, the session keeps the user signed in across requests.

Session Formats

  • Cookies (httpOnly, Secure, SameSite=Strict): Sent automatically on every request; can't be stolen by JavaScript; CSRF-protected.
  • Bearer tokens in Authorization header: Require explicit JavaScript; good for APIs and multi-domain scenarios.
  • Hybrid (recommended): Use cookies for web apps, accept bearer tokens for API calls from other services.

Session Lifetime

  • Short-lived (15 min): Limits exposure if a session token leaks.
  • Refresh tokens (7 days): Used to mint a new short-lived session without re-authenticating.
  • Explicit logout: Invalidate the session immediately; don't rely on expiry alone.
Never store secrets in URLs. Use POST request bodies or Authorization headers. URLs are logged by proxies, CDNs, and browser history. Redirect after a sign-in POST to hide the token from the URL.

Security Model: Trust Boundaries

What Your App Must Do

  • Validate session on every request: Don't cache auth state. Middleware should verify the token/cookie fresh each time.
  • Scope database queries: Always filter by the authenticated user_id. A missing filter is a data leak.
  • Never trust user input for auth: A ?user_id=123 query param is not proof the user is 123. Verify against the session.
  • Handle errors safely: Don't leak whether an email exists, whether a session is valid, or why a request failed. Log details server-side; show generic errors to the client.

What Your App Must NOT Do

  • Embed tokens in URLs or HTML data attributes (they're visible in logs and history).
  • Relax CSRF protection for "convenience" (e.g., accepting JSON requests without a CSRF token). If cookies carry auth, CSRF protection is mandatory.
  • Reuse session cookies across domains. Mark them with __Host- or __Secure- prefixes.
  • Store passwords in plaintext, even in logs. Use hashed/salted passwords or managed services only.

Defense in Depth

Layer multiple checks:

Layer What It Stops
httpOnly cookies JavaScript theft (XSS)
SameSite=Strict Cross-site requests (CSRF)
Server-side session validation Forged tokens, replayed sessions
Scoped database queries Permission escalation, lateral data leaks
HTTPS + Secure flag Man-in-the-middle attacks

Common Pitfalls

1. Storing Secrets in Environment

Problem: OAuth client secret checked into version control.

Solution: Use injected environment variables in production. In development, keep secrets in a local `.env` file (never committed). Rotate secrets annually and immediately if exposed.

2. Leaking User IDs in URLs

Problem: /dashboard?user_id=42 looks like a user ID and is tempting to increment.

Solution: Never expose internal IDs in URLs. Use the session to determine the user. If a URL must name something, use an opaque token (UUID v4) or slug, never an incrementing integer.

3. Silent Failures

Problem: A missing auth middleware means a public endpoint leaks data.

Solution: Middleware should be the default. Make protected routes the common case; public routes the exception. Use a linter rule to flag createServerFn without auth middleware.

4. Forgetting Logout

Problem: "Sign out" button clears the client-side session but doesn't invalidate the server token.

Solution: Logout must hit the server. Revoke the session token, invalidate the refresh token, and only then clear client-side state. A server-side logout is mandatory; client-side only is a false logout.

Implementation Checklist

  • ☐ Identity provider chosen: OAuth (Google/X) + email/password hybrid, or managed service
  • ☐ OAuth credentials registered with each provider
  • ☐ Session broker configured: cookie flags set (httpOnly, Secure, SameSite=Strict)
  • ☐ Server-side session validation middleware in place on all protected routes
  • ☐ Database queries scoped to authenticated user_id; no user-supplied IDs in WHERE clauses
  • ☐ Logout endpoint implemented; server-side session revocation working
  • ☐ Error messages are generic; no leaking of user existence or session validity
  • ☐ No secrets in URLs, logs, or HTML attributes
  • ☐ CSRF protection enabled for cookie-based auth
  • ☐ HTTPS enforced; Secure flag set on session cookies
  • ☐ Password reset flow tested (email verification, token expiry, rate limiting)
  • ☐ Session timeout configured; refresh token expiry enforced
