Serverless PostgreSQL: Database Design for Scale

Production guide to serverless PostgreSQL: connection pooling, migrations, per-user data patterns, and development/production parity.

Why PostgreSQL, and Why Serverless

PostgreSQL is the default choice for production systems: ACID transactions, rich types, indexing, and SQL itself are proven for 30 years. Serverless PostgreSQL (like Neon) removes infrastructure burden while keeping every feature: pay per connection-minute, no capacity planning, instant scaling.

Serverless works well for:

  • Multi-tenant SaaS where per-user data must be isolated and scoped server-side
  • Rapid prototyping where schema changes are frequent and you need instant migrations
  • Bursty traffic where you don't want to reserve capacity for peak load
  • Regional deployments where you want a database close to your servers
Key constraint: Serverless databases use connection pooling to share connections. This means you cannot rely on session state (SET statements, temporary tables, advisory locks). Keep sessions stateless.

Development vs. Production: Choose Parity

A common problem: development uses SQLite or mock data, production uses PostgreSQL. The two behave differently, and bugs only appear in production.

Better approach: Use the same database engine in development as production. Serverless PostgreSQL supports this with a lightweight fallback:

  • Configured (env var set, e.g. deployed): Real Neon PostgreSQL
  • Not configured (sandbox live preview): Embedded PGLite (Postgres in WebAssembly), same SQL semantics

Both modes work with the same driver and the same query API. This means you develop against real SQL, catch bugs early, and deploy with confidence.

// Same code, same API, different backend
import { getSql } from '@/lib/db';

const sql = await getSql();
// In dev: PGLite (in-process, zero config)
// In prod: Neon (real PostgreSQL, connection pool)
return sql<{ id: number; title: string }>`
  SELECT id, title FROM posts ORDER BY id DESC
`;

Migrations: Schema as Code

Migrations are your source of truth for the schema. Never create tables by hand or through a GUI. Write SQL, version it, and apply it to every environment in the same order.

Structure

Store migrations in migrations/ directory, numbered and ordered:

migrations/
  0001_users.sql
  0002_posts.sql
  0003_add_tags.sql

Pattern

Each migration is idempotent. Use CREATE TABLE IF NOT EXISTS so re-running a migration doesn't fail:

-- migrations/0001_users.sql
CREATE TABLE IF NOT EXISTS users (
  id         SERIAL PRIMARY KEY,
  email      TEXT NOT NULL UNIQUE,
  user_id    TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS users_email_idx ON users (email);

Development Workflow

  1. Write a new migration: migrations/0002_posts.sql
  2. Start the dev server. The migration runs automatically on PGLite startup.
  3. Test your queries against the new schema.
  4. On deploy, the build step runs all migrations against Neon before shipping.
Never edit an applied migration. It is tracked by name in _migrations

Per-User Data: The Scoping Rule

In multi-user systems, every query must be scoped to the authenticated user. This is not optional—it is your primary defense against data leaks.

The Pattern

Every user-owned table gets a user_id column:

CREATE TABLE todos (
  id         SERIAL PRIMARY KEY,
  user_id    TEXT NOT NULL,
  title      TEXT NOT NULL,
  done       BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX todos_user_id_idx ON todos (user_id);

On every query, filter by user:

import { authMiddleware } from '@/lib/auth/middleware';

export const listTodos = createServerFn()
  .middleware([authMiddleware])  // Verify session
  .handler(async ({ context }) => {
    const sql = await getSql();
    // Always scope: context.userId is verified by middleware
    return sql<{ id: number; title: string }>`
      SELECT id, title FROM todos
      WHERE user_id = ${context.userId}
      ORDER BY id DESC
    `;
  });

Mutations Must Also Scope

Not just reads—every write must scope to the user:

// WRONG: Missing scope
UPDATE todos SET done = true WHERE id = ${todoId};

// RIGHT: Scope the update
UPDATE todos
  SET done = true
  WHERE id = ${todoId} AND user_id = ${context.userId};

The second update protects against a user guessing another user's todo ID and marking it done. Without the AND user_id = …, it would succeed.

Trust the driver, not the user. A Postgres client library has full database access. The only check is your WHERE clause. An unscoped query is a lateral data leak waiting to happen.

Connection Pooling and Stateless Sessions

Serverless databases like Neon use pooling to share connections across many requests. This means you cannot rely on session state.

What Doesn't Work

  • SET variable = value — pooling may route the next query to a different physical connection
  • Temporary tables — created in one connection, invisible from another
  • Advisory locks — session-specific, don't work across connections
  • LISTEN/NOTIFY — session notifications don't reach pooled connections

What Works

  • Standard SQL: SELECT, INSERT, UPDATE, DELETE, transactions within a single query
  • Indexes and constraints (live in the database, not the connection)
  • Prepared statements (compiled server-side, reusable)
  • Explicit scoping: WHERE user_id = $1

Think of each query as stateless. Pass all context in parameters, not in connection state.

Query Patterns and Performance

Avoid N+1 Queries

Loading a list of posts, then fetching the author for each post, is O(N) database calls:

// SLOW: N+1 query pattern
const posts = await sql`SELECT * FROM posts WHERE user_id = ${userId}`;
for (const post of posts) {
  const author = await sql`SELECT * FROM users WHERE id = ${post.author_id}`;
  post.author = author;
}

Better: Join or use a batch query:

// BETTER: Single query with join
const posts = await sql`
  SELECT p.*, u.name as author_name
  FROM posts p
  LEFT JOIN users u ON p.author_id = u.id
  WHERE p.user_id = ${userId}
`;

Indexes for Common Filters

If you always filter by a column, index it:

CREATE INDEX IF NOT EXISTS posts_user_id_idx ON posts (user_id);
-- After adding this index, queries with WHERE user_id = X run in milliseconds

Type Safety

Always declare result types to catch schema mismatches:

// Declares the shape of each row
const posts = await sql<{
  id: number;
  title: string;
  created_at: string;  // Dates come back as ISO strings
}>`SELECT id, title, created_at FROM posts`;

Development ↔ Production Parity

PGLite (Development)

  • In-memory, wiped on dev-server restart
  • Single connection (no concurrency or locking)
  • No extensions (don't CREATE EXTENSION)
  • Perfect for catching SQL errors early

Neon (Production)

  • Persistent network database
  • Connection pool (stateless sessions)
  • Network latency: queries may take 10–100ms
  • Cold resume: scaling from zero takes a few seconds

Differences to Respect

Feature PGLite (Dev) Neon (Prod)
Transactions ✓ Work fine ✓ Work fine
Session state (SET) ✓ Works ✗ Pooled away
Concurrent writes ✗ Single connection ✓ Full support
Latency <1ms 10–100ms
user_id type TEXT ('dev-user') TEXT (from auth)

Checklist

  • ☐ Migrations tracked in migrations/, ordered, idempotent
  • ☐ Every user-owned table has user_id TEXT NOT NULL column
  • ☐ All queries scoped by WHERE user_id = ${context.userId}
  • ☐ Mutations also scoped: UPDATE/DELETE include user_id in WHERE
  • ☐ No session state (SET statements) relied upon
  • ☐ Type-safe query results declared
  • ☐ Indexes on frequently filtered columns
  • ☐ N+1 queries eliminated (use joins or batch queries)
  • ☐ DATABASE_URL injected in production, unset in development (uses PGLite)
  • ☐ Dev-server queries tested against PGLite before deploy

Evidence-first engineering. This guide reflects patterns from the Grok Build framework and tested against both PGLite and Neon PostgreSQL.
