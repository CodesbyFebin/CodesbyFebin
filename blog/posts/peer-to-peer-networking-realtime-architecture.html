Peer-to-Peer Networking: Real-Time Multiplayer Architecture

Learn WebRTC peer-to-peer mesh for low-latency multiplayer: signaling, connection patterns, and trust models for co-op gaming.

Why P2P for Multiplayer

Traditional multiplayer sends all game traffic through a server. P2P lets players connect directly to each other, with the server handling only the connection handshake. Result: browser-to-browser latency (often 5–40ms) instead of browser-to-server-to-browser (50+ ms).

Use P2P when: 2–8 players, co-op or casual play among friends, shared cursors, drawing, party games, casual action.

Don't use P2P for: Competitive ranking, cheat-sensitive games, or anonymous-stranger matchmaking. P2P has no server authority—every peer runs its own copy of the rules and can lie about position, score, or anything else.

Trust model: P2P is for co-op and casual play among people who choose to play together. Peers see each other's IP addresses during connection; competitive or cheat-sensitive play requires server authority (not P2P).

Full Mesh Topology

All visitors on the same domain form one "room" and open a WebRTC data channel to every other visitor. For N peers, that's N×(N-1)/2 connections (O(N²) scaling).

Players Connections Practical?
2 1 ✓ Yes
4 6 ✓ Yes
8 28 ✓ Cap at 8
16 120 ✗ Too many

Limit rooms to ~8 peers. Each peer opens 7 connections; mobile browsers start to struggle beyond that.

Signaling Relay: The Only Server

Peers need to know each other's network addresses before connecting. A signaling relay at /api/rtc brokers the handshake only—game traffic never touches it.

The flow:

  1. Peer A generates an offer (SDP)
  2. Peer A posts it to /api/rtc; relay stores it
  3. Peer B polls /api/rtc and fetches Peer A's offer
  4. Peer B generates an answer (SDP) and posts it back
  5. Both peers post ICE candidates (network addresses)
  6. Relay relays candidates between them
  7. Peers connect directly; relay goes silent
// The signaling relay is simple:
// GET /api/rtc?room=lobby → returns offers/answers/ICE for this room
// POST /api/rtc → stores an offer/answer/ICE candidate

// Peers poll GET every 100ms, post SDP on state changes
const p2p = new P2PRoom({
  room: 'lobby',
  selfId: myId,
  onPeersChanged: (peers) => render(peers),
  onMessage: (from, data) => gameState.apply(from, data)
});

await p2p.join();
p2p.broadcast(gameState);  // Unreliable, game-rate (~20/s)
p2p.send(event);            // Reliable, exactly-once

Two Message Channels

Each peer-to-peer connection carries two data channels:

Channel Reliability Use
"state" Unreliable, unordered Position, cursor, continuously-refreshed state
"events" Reliable, ordered One-shot events: jump, attack, take damage

Why two? State broadcasts at game rate (~20 Hz). Late packets are stale and dropped. Events must arrive exactly-once or the game breaks (you died twice, or not at all). Unreliable state is fast; reliable events are slow but certain.

// Broadcast position every frame (unreliable, stale drops OK)
p2p.broadcast({ pos: [x, y], angle: dir });

// Send attack event (reliable, must arrive exactly once)
p2p.send({ type: 'attack', target: enemyId });

Late Joiners

When a new peer joins, the existing peers don't automatically send state—late joiners would start with no knowledge of the game world.

Pattern: When a new peer appears in p2p.peers, an existing peer (selected by comparing IDs) sends the current shared state:

// On every peer change, check if we should answer a newcomer
onPeersChanged: (peers) => {
  for (const newPeer of peers) {
    if (newPeer.isNew) {
      // Answer only if our ID is the smallest among existing peers
      // This ensures exactly one peer sends the state
      const existingIds = peers.filter(p => !p.isNew).map(p => p.id);
      if (iSmallestId(myId, existingIds)) {
        p2p.send({ type: 'init', world: gameState }, newPeer.id);
      }
    }
  }
};

Handling Connection Failures

Roughly 10–20% of peer pairs sit behind strict NATs and cannot connect directly. The signaling relay will detect this as connectionState: "failed".

Show it in the UI instead of hanging:

  • If all peers are connected: green, game plays normally
  • If one peer has failed connections: yellow warning, game may be desynchronized
  • If many connections fail: red, ask players to restart or use a different device

To override the default STUN server, set VITE_STUN_URLS in .grok/app-env.json and restart the dev server.

Peer Disappearance

Peers disappear without goodbye: a tab close, device sleep, or network loss. Treat a peer missing from p2p.peers as gone immediately:

  • Drop its entities from the game world
  • Stop rendering its position or cursor
  • Don't wait for a "goodbye" message

Implementation Checklist

  • ☐ Room capped at ~8 peers
  • ☐ Signaling relay implemented at /api/rtc
  • ☐ Two channels: unreliable state + reliable events
  • ☐ Late joiners: one existing peer sends init state
  • ☐ UI shows connection state per peer (green/yellow/red)
  • ☐ Peers disappear are handled immediately (drop entities)
  • ☐ No server authority assumed (game is co-op only)
  • ☐ Diagnostics available: p2p.peers[i].rttMs, connectionState
